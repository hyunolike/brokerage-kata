# 코드 리뷰 (코칭)

## 준비
1. `./kata status`로 현재 문제·단계를 확인한다. (`$ARGUMENTS`에 문제가 있으면 그것을 우선)
2. 읽을 것: 문제 `README.md`의 평가 포인트, 현재 단계까지의 문서(트랙 B·C는 constitution, spec, plan, tasks, `docs/adr/`), 사용자의 `src`/`tests`, `NOTES.md`, `git diff`/`git log`(작은 걸음으로 진행했는지).
   그리고 채점 기준인 `docs/guides/clean-code.md`를 읽는다. (Kotlin 코드면 `CC-K*`도 적용)
3. 테스트를 실행해 현재 상태를 확인한다.

## 출력 형식
```
## 리뷰 — <문제> stage <N>

### 잘한 점 (2~3개, 구체적으로 파일:라인)

### 요구사항 누락 / 버그 가능성
- 코드를 고쳐 주지 말고 **실패할 입력**이나 **질문**으로 제시한다.
  예: "SELL 주문이 최우선 매수가와 같은 가격으로 들어오면 어떻게 되나요? 테스트로 확인해 보세요."

### 설계 (평가 포인트별)
| 평가 포인트 | 평가 (상/중/하) | 근거 |

### 클린코드 (docs/guides/clean-code.md)
| ID | 심각도 | 위치 (파일:라인) | 무엇이 문제인가 (고치는 방법은 쓰지 않는다) |
- 🔴 항목부터, 최대 7개. 해당 없는 카테고리는 생략한다.

### 아키텍처 (트랙 B)
- ADR-0000 의 결정과 실제 패키지/의존 구조가 일치하는가, `Stage1ArchitectureTest`가 그 결정을 실제로 검증하는가

### 면접관 꼬리 질문 (3개)

### 다음 단계로 가기 전 1가지만 고친다면
```

- 수정 코드 전체를 쓰지 않는다. 필요하면 **언어 일반 관용구**만 문제와 무관한 예시로 보여준다.
- "좋아요" 같은 빈 칭찬, 모호한 지적("더 깔끔하게") 금지. 모든 지적에는 근거와 확인 방법을 붙인다.
- 다음 단계 요구사항을 근거로 설계를 비판하지 않는다. (다음 단계는 사용자가 아직 모른다)
- 패턴 이름을 처방하지 않는다. "전략 패턴을 쓰세요"(X) → "새 유형이 추가되면 이 파일에서 몇 군데를 고치게 되나요? (CC-O5)"(O)
