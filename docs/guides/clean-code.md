# 클린코드 체크리스트

> `/review`는 이 체크리스트의 **ID**(예: `CC-N2`)를 근거로 지적한다. 스스로 리뷰할 때도 같은 기준을 쓴다.
> 규칙은 목적이 아니다. 각 항목의 "왜"를 설명할 수 없으면 그 규칙은 지키지 않아도 된다.

심각도: 🔴 반드시(버그·정확성) · 🟡 권장(유지보수성) · ⚪ 취향(팀 컨벤션에 따름)

## N. 이름

| ID | 항목 | 심각도 |
|---|---|---|
| CC-N1 | 이름만 보고 **무엇을/왜** 하는지 안다. `data`, `info`, `process`, `handle`, `temp` 금지 | 🟡 |
| CC-N2 | 도메인 용어를 쓴다 (주문, 체결, 잔량, 호가 단위). 같은 개념에 두 단어를 쓰지 않는다 | 🟡 |
| CC-N3 | boolean 은 `is/has/can`, 메서드는 동사, 컬렉션은 복수형 | ⚪ |
| CC-N4 | 약어 금지 (`amt`, `qty`, `prc` → `amount`, `quantity`, `price`) | 🟡 |

## F. 함수

| ID | 항목 | 심각도 |
|---|---|---|
| CC-F1 | 한 함수는 한 가지 일, 한 추상화 수준 | 🟡 |
| CC-F2 | 길이 약 20줄, 들여쓰기 2단계 이내 (넘으면 이유가 있어야 한다) | 🟡 |
| CC-F3 | 파라미터 3개 이하. 늘 함께 다니면 객체로 묶는다 | 🟡 |
| CC-F4 | 조회와 변경을 분리한다 (Command-Query Separation) | 🟡 |
| CC-F5 | boolean 플래그 파라미터로 동작을 바꾸지 않는다 | 🟡 |
| CC-F6 | early return / guard clause 로 중첩을 줄인다 | ⚪ |

## O. 객체와 설계

| ID | 항목 | 심각도 |
|---|---|---|
| CC-O1 | 규칙은 데이터가 있는 객체에 둔다. getter 로 꺼내 밖에서 판단하지 않는다 (Tell, Don't Ask) | 🟡 |
| CC-O2 | 불변을 기본으로. `record`, `final` 필드, 방어적 복사, 변경 메서드는 새 객체 반환 또는 명시적 상태 전이 | 🟡 |
| CC-O3 | 원시 타입 집착(Primitive Obsession) 없음 — 의미 있는 값은 타입으로 | 🟡 |
| CC-O4 | 한 클래스는 변경 이유가 하나 (SRP). "그리고"로 설명되면 쪼갠다 | 🟡 |
| CC-O5 | 새 유형이 추가될 때 기존 `switch/if` 를 여러 곳 고쳐야 한다면 구조를 의심한다 (OCP) | 🟡 |
| CC-O6 | 구현이 아니라 역할(인터페이스)에 의존한다. 단, 구현이 하나뿐인 인터페이스를 습관적으로 만들지 않는다 | ⚪ |
| CC-O7 | 잘못된 상태의 객체가 만들어질 수 없다 (생성 시점 검증) | 🔴 |
| CC-O8 | 전역 가변 상태(static 가변 필드) 없음 | 🔴 |

## E. 오류 처리

| ID | 항목 | 심각도 |
|---|---|---|
| CC-E1 | 예외를 삼키지 않는다 (`catch (Exception e) {}` 금지) | 🔴 |
| CC-E2 | 실패 이유를 호출자가 구분할 수 있다 (도메인 예외 또는 에러 코드) | 🟡 |
| CC-E3 | `null` 반환 대신 `Optional`(조회), 예외(규칙 위반), 빈 컬렉션 | 🟡 |
| CC-E4 | 매직 넘버·매직 문자열 대신 이름 있는 상수/enum. 에러를 `-1` 같은 값으로 알리지 않는다 | 🟡 |
| CC-E5 | 검증 실패 시 상태가 바뀌지 않는다 (부분 변경 금지) | 🔴 |

## M. 돈과 숫자

| ID | 항목 | 심각도 |
|---|---|---|
| CC-M1 | 금액에 `double/float` 금지. 원화는 `long` 또는 `BigDecimal`, 외화는 `BigDecimal` | 🔴 |
| CC-M2 | `BigDecimal` 은 `valueOf`/문자열 생성, 비교는 `compareTo`, 나눗셈은 scale 과 `RoundingMode` 명시 | 🔴 |
| CC-M3 | 반올림 정책이 한곳에 모여 있다 | 🟡 |
| CC-M4 | 곱셈 오버플로 가능성을 검토했다 (`Math.multiplyExact` 등) | 🟡 |

## C. 동시성

| ID | 항목 | 심각도 |
|---|---|---|
| CC-C1 | check-then-act 가 원자적이다 | 🔴 |
| CC-C2 | 락 범위가 최소이고, 락 안에서 I/O·외부 호출을 하지 않는다 | 🟡 |
| CC-C3 | 공유 가변 상태의 가시성이 보장된다 (`volatile`, 동시성 컬렉션, 락) | 🔴 |
| CC-C4 | 락 획득 순서가 일정하다 (데드락 방지) | 🔴 |

## T. 테스트

| ID | 항목 | 심각도 |
|---|---|---|
| CC-T1 | 테스트 이름이 요구사항 문장이다 (`@DisplayName`, AC 번호) | 🟡 |
| CC-T2 | given / when / then 이 구분되고, 테스트 하나는 개념 하나 | 🟡 |
| CC-T3 | 구현 세부가 아니라 **행위**를 검증한다 (리팩터링하면 깨지는 테스트는 의심) | 🟡 |
| CC-T4 | 경계값을 테스트한다 (0, 1, 최대, 정확히 한도, 한도+1) | 🔴 |
| CC-T5 | 테스트끼리 독립적이다 (순서, 공유 상태, 현재 시각에 의존하지 않음) | 🔴 |
| CC-T6 | 동시성 테스트는 동시에 출발시키고 결과를 결정적으로 검증한다 | 🔴 |

## S. Spring / JPA (트랙 B)

| ID | 항목 | 심각도 |
|---|---|---|
| CC-S1 | 생성자 주입, 필드 주입 금지 | 🟡 |
| CC-S2 | 엔티티를 API 요청/응답으로 직접 쓰지 않는다 | 🟡 |
| CC-S3 | 트랜잭션 경계가 명확하다. 조회는 `readOnly`, 외부 호출은 트랜잭션 밖 | 🟡 |
| CC-S4 | 같은 클래스 내부 호출로 `@Transactional`, `@Async` 가 무시되지 않는다 (프록시) | 🔴 |
| CC-S5 | N+1 쿼리를 확인했다 | 🟡 |
| CC-S6 | 엔티티에 무분별한 setter 가 없다. 변경은 의도가 드러나는 메서드로 | 🟡 |
| CC-S7 | 설정값(시간 제한, 한도)은 코드 대신 설정으로 뺄지 검토했다 | ⚪ |

## K. Kotlin 으로 풀 때

| ID | 항목 | 심각도 |
|---|---|---|
| CC-K1 | `!!` 를 쓰지 않는다. null 가능성은 타입으로 표현 | 🔴 |
| CC-K2 | `val` 기본, 가변 컬렉션은 외부에 노출하지 않는다 | 🟡 |
| CC-K3 | 상태/결과 표현에 `sealed class/interface` + `when` 을 검토 | ⚪ |
| CC-K4 | `data class` 를 JPA 엔티티에 쓰지 않는다 (equals/hashCode, 프록시) | 🔴 |

## 셀프 리뷰 순서 (5분)

1. 🔴 항목만 먼저 훑는다 — 돈, 동시성, 상태 불변식, 예외 삼킴
2. 테스트 이름만 읽어 요구사항이 보이는지 확인한다
3. 가장 긴 함수 1개, 가장 큰 클래스 1개를 골라 F·O 항목으로 본다
