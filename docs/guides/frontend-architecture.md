# 프론트엔드 아키텍처 선택 가이드 (트랙 C)

> [백엔드 가이드](architecture.md)와 같은 원칙: **정답이 아니라 선택지와 판단 기준**이다.
> 결정은 `track-c-frontend/specs/001-account-dashboard/plan.md`의 "0. 아키텍처 결정"에 적고,
> 이후 spec(C002~)은 그 결정을 따르거나, 바꾼다면 이유를 적는다.

백엔드 개발자에게 프론트엔드 설계의 핵심 질문은 하나로 모인다. **"이 상태는 누구의 것이고, 어디에 살아야 하는가?"**

## 1. 상태를 먼저 분류한다

| 종류 | 예 (이 과제에서) | 진실 공급원 | 흔한 실수 |
|---|---|---|---|
| **서버 상태** | 잔고, 주문 목록 | 서버 | 클라이언트 state 에 복사해 두고 동기화를 직접 관리 |
| **폼 상태** | 입력 중인 수량·가격, 필드 오류 | 폼 | 매 입력마다 전역 상태를 갱신 |
| **UI 상태** | 모달 열림, 선택된 필터 탭 | 컴포넌트 | 전역 스토어에 올림 |
| **URL 상태** | 현재 페이지, 필터, 계좌 ID | URL | 새로고침하면 사라지는 곳에 둠 |
| **파생 상태** | 예상 주문 금액, 주문 가능 여부 | 계산 (저장하지 않음) | `useState` + `useEffect`로 동기화 |

## 2. 선택지

### 서버 상태 관리

| 선택지 | 장점 | 단점 | 신호 |
|---|---|---|---|
| 직접 구현 (`useEffect` + `fetch` + 커스텀 훅) | 의존성 없음, 동작을 전부 이해 | 캐시, 중복 요청 제거, 경쟁 조건, 재시도, 무효화를 직접 구현 | 화면 1~2개, 학습 목적 |
| 서버 상태 라이브러리 (TanStack Query, SWR 등) | 캐시·무효화·재시도·로딩 상태 표준화 | 학습 비용, "왜 필요한지"를 설명할 수 있어야 함 | 같은 데이터를 여러 화면이 공유, 변경 후 재조회가 많음 |

> 한 번은 직접 구현해 보고, 어떤 문제를 만난 뒤 라이브러리로 바꾸는 것도 좋은 연습이다. (그 과정을 plan 에 기록)

### 폴더 구조

| 방식 | 예 | 장점 | 단점 |
|---|---|---|---|
| 레이어별 | `components/`, `hooks/`, `api/`, `pages/` | 단순, 익숙함 | 기능 하나를 고치려면 폴더 4개를 오간다 |
| 기능별 | `features/account/`, `features/order/` 아래에 각각 | 기능 경계가 보인다, 백엔드의 기능 기준 패키지와 대응 | 공용 코드(`shared/`)의 경계를 정해야 한다 |
| Feature-Sliced Design 등 규약 | `app/pages/widgets/features/entities/shared` | 규칙이 명확, 큰 팀에 유리 | 작은 과제에는 층이 많다 |

### API 계층

| 결정 | 선택지 |
|---|---|
| 호출 계층 | 컴포넌트에서 `fetch` 직접 / 공통 `request()` → 기능별 API 함수 → 훅 |
| 타입 | 손으로 작성 / 계약(`contracts/brokerage-api.yaml`)에서 생성 (openapi-typescript 등) |
| 에러 | 예외로 던지기 / 결과 타입(`{ ok, data } | { ok: false, error }`)으로 돌려주기 |
| 목(mock) | 모듈 목킹(`vi.mock`) / 네트워크 수준 목(MSW 등) / 고정 JSON |

### 컴포넌트 구성

| 방식 | 신호 | 주의 |
|---|---|---|
| 커스텀 훅으로 로직 분리 | 컴포넌트에 데이터 조회·검증·제출 로직이 섞여 길어진다 | 훅이 모든 것을 반환하는 "갓 훅"이 되지 않게 |
| 표현(presentational) / 컨테이너 분리 | 같은 UI 를 다른 데이터로 재사용, 테스트에서 UI 만 검증하고 싶다 | 훅이 있으면 과거만큼 필수는 아니다 |
| 합성(compound) 컴포넌트 | 부모-자식이 상태를 공유하는 UI (탭, 필터) | 작은 과제에서는 과하다 |

### 순수 로직의 위치

호가 단위 검증, 금액 포맷, 에러 코드 → 메시지 매핑처럼 **React 와 무관한 규칙**을 어디에 둘지 정한다.
(`lib/`, `domain/`, 기능 폴더 안 등) 이 코드는 컴포넌트 없이 단위 테스트할 수 있어야 한다.

## 3. 결정할 때 스스로 답할 질문

1. 잔고는 주문 성공 후 어떻게 최신이 되는가? (재조회? 응답으로 갱신? 누가 책임지나?)
2. 같은 잔고를 두 화면(대시보드, 주문 폼)이 쓸 때 요청은 몇 번 나가는가?
3. 주문 버튼 중복 클릭은 어느 층에서 막는가? 서버 멱등 키와는 어떻게 연결되는가?
4. 계약이 바뀌면 컴파일 에러로 알 수 있는가?
5. 테스트는 무엇을 목킹하는가? 그 경계가 실제 버그를 놓치지 않는가?
6. 백엔드의 기능 경계(001 계좌, 002 주문)와 프론트엔드 폴더 경계가 대응하는가? 대응해야 하는가?

## 4. 면접 꼬리 질문 대비

- "서버 상태와 클라이언트 상태를 어떻게 구분했나요?"
- "`useEffect` 로 데이터를 가져올 때 생길 수 있는 경쟁 조건은?"
- "낙관적 업데이트를 돈이 걸린 화면에 썼나요? 왜?"
- "이 라이브러리를 빼면 무엇을 직접 구현해야 하나요?"
