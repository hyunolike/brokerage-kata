# 디자인 패턴 카탈로그

> 패턴은 **문제가 먼저 보이고 나서** 꺼내는 도구다. 이 문서는 "어떤 신호가 보이면 어떤 패턴을 검토할지"만 정리한다.
> 어느 문제에 어느 패턴이 맞는지는 일부러 적지 않았다. 그 연결을 스스로 찾는 것이 연습이다.

각 항목: **신호**(이런 코드/요구가 보이면) · **효과** · **과용 주의**

## 1. 도메인 모델링 (DDD 전술 패턴)

| 패턴 | 신호 | 효과 | 과용 주의 |
|---|---|---|---|
| **값 객체 (Value Object)** | 같은 원시 타입(`long`, `String`)이 다른 의미로 여기저기 전달된다. 검증 코드가 반복된다 | 생성 시점에 불변식 보장, 의미 있는 이름, 불변 | 모든 필드를 감싸면 매핑 비용만 늘어난다 |
| **엔티티 (Entity)** | 속성이 바뀌어도 같은 대상으로 추적해야 한다 (식별자) | 동일성 기준 명확화 | `equals/hashCode`를 식별자로 정할 때 JPA 프록시 주의 |
| **애그리거트 (Aggregate)** | 여러 객체가 **함께** 일관돼야 하는 규칙이 있다 | 일관성 경계 = 트랜잭션 경계 = 락 단위 | 너무 크게 잡으면 동시성 경합이 커진다 |
| **도메인 서비스** | 규칙이 어느 한 객체에 속하지 않는다 (두 애그리거트에 걸침) | 규칙의 위치를 명시 | 모든 로직을 서비스로 빼면 빈 도메인이 된다 |
| **도메인 이벤트** | "A가 일어나면 B도 해야 한다"는 후속 처리가 늘어난다 | 결합도 감소, 외부 발행(Kafka)과 자연스럽게 연결 | 흐름 추적이 어려워진다. 같은 트랜잭션 안의 일은 직접 호출이 낫다 |
| **리포지토리** | 저장 방식과 도메인을 분리하고 싶다 | 도메인은 컬렉션처럼 다룸 | Spring Data 인터페이스를 도메인에 그대로 노출하면 분리 효과가 없다 |
| **팩토리 / 정적 생성 메서드** | 생성 규칙이 복잡하거나 생성 방법이 여러 가지다 | 의도가 드러나는 이름 (`ofMarket`, `ofLimit`) | 단순 생성까지 팩토리로 감싸지 않는다 |

## 2. 행위 (GoF)

| 패턴 | 신호 | 효과 | 과용 주의 |
|---|---|---|---|
| **전략 (Strategy)** | 같은 계산을 조건에 따라 다르게 한다. `if (type == A) ... else if (type == B)` 가 여러 곳에 반복 | 분기를 한곳으로, 새 경우 = 새 클래스 | 경우가 2개이고 늘 일이 없다면 if 가 더 읽기 쉽다 |
| **상태 (State) / 상태 머신** | 상태에 따라 허용되는 동작이 다르다. 잘못된 전이를 막아야 한다 | 허용 전이를 구조로 표현 | Java 에서는 `enum` + 메서드 또는 `sealed interface` 가 더 가벼운 대안 |
| **템플릿 메서드** | 알고리즘 뼈대는 같고 한두 단계만 다르다 | 중복 제거 | 상속 결합. 전략(조합)으로 대체 가능한지 먼저 본다 |
| **책임 연쇄 (Chain of Responsibility)** | 검증·정책을 순서대로 여러 개 적용한다. 규칙이 계속 추가된다 | 규칙 추가 시 기존 코드 불변 | 순서 의존성이 숨는다. 순서를 테스트로 고정 |
| **명세 (Specification)** | 조건 조합(AND/OR)이 많고 재사용된다 | 조건을 이름 있는 객체로 | 조건이 적으면 과하다 |
| **옵저버 / 이벤트 리스너** | 하나의 변화에 여러 후속 반응이 붙는다 | 발행자와 구독자 분리 | 동기/비동기, 트랜잭션 커밋 전/후 시점을 명확히 (`@TransactionalEventListener`) |

## 3. 구조 (GoF)

| 패턴 | 신호 | 효과 | 과용 주의 |
|---|---|---|---|
| **어댑터** | 외부 시스템(시세, 환율, 거래소)의 인터페이스가 내 모델과 다르다 | 외부 변화의 영향 차단, 테스트 대역 주입 | |
| **데코레이터** | 기능 위에 부가 기능(캐시, 로깅, 재시도, 락)을 덧씌운다 | 핵심 로직과 부가 기능 분리 | Spring AOP 와 역할이 겹친다 |
| **퍼사드** | 호출부가 여러 객체를 순서대로 다뤄야 한다 | 단순한 진입점 | 퍼사드에 로직이 쌓이면 새 "갓 클래스" |

## 4. 레거시 개선 (리팩터링 기법)

| 기법 | 신호 | 효과 |
|---|---|---|
| **특성 테스트 (Characterization Test)** | 동작의 "정답"을 모르는 코드를 고쳐야 한다 | 현재 동작을 안전망으로 고정 |
| **Seam 도입 (의존성 주입, Clock 주입)** | `new Date()`, static 호출, 싱글턴 때문에 테스트가 안 된다 | 테스트 가능한 틈 확보 |
| **Extract Method → Move Method** | 긴 메서드, 한 메서드가 여러 객체의 데이터를 만진다 | 책임이 데이터가 있는 곳으로 |
| **조건문을 다형성으로 (Replace Conditional with Polymorphism)** | 같은 조건 분기가 여러 메서드에 반복 | 분기 제거 |
| **매개변수 객체 (Introduce Parameter Object)** | 파라미터가 6개를 넘고 늘 함께 다닌다 | 시그니처 안정, 새 입력 추가 쉬움 |
| **스트랭글러 / 병행 구현** | 공개 시그니처를 바꿀 수 없다 | 기존 진입점은 유지하고 내부만 새 구조로 위임 |

## 5. 분산·실무 패턴 (트랙 B 이후)

| 패턴 | 신호 | 효과 | 주의 |
|---|---|---|---|
| **멱등 키 (Idempotency Key)** | 클라이언트 재시도로 같은 요청이 두 번 온다 | 중복 처리 방지 | 키 저장소, 보관 기간, 동시 첫 요청 처리 |
| **낙관적 락 / 비관적 락 / 조건부 UPDATE** | 같은 행을 동시에 갱신한다 | 갱신 손실 방지 | 경합 빈도에 따라 선택 |
| **분산 락** | 여러 인스턴스가 DB 밖의 자원 또는 DB 락으로 풀기 어려운 구간을 공유 | 인스턴스 간 상호 배제 | 락 만료, 락 서버 장애, 트랜잭션과 락 해제 순서 |
| **트랜잭셔널 아웃박스 (Transactional Outbox)** | DB 저장과 메시지 발행이 **둘 다 되거나 둘 다 안 돼야** 한다 | 이중 쓰기 문제 해결 | 발행 지연, 중복 발행 → 소비자 멱등 필요 |
| **멱등 소비자 (Idempotent Consumer)** | 메시지는 최소 한 번(at-least-once) 전달된다 | 중복 메시지 무해화 | 처리 기록과 비즈니스 변경을 같은 트랜잭션에 |
| **CQRS (가벼운 형태)** | 조회 요구가 쓰기 모델과 모양이 다르다 | 조회 모델 분리 | 작은 과제에서는 조회 전용 쿼리 메서드 정도로 충분 |

## 스스로 점검

- 이 패턴을 빼면 코드가 **실제로** 나빠지는가? 아니면 "패턴을 쓴 코드"를 보여주고 싶은가?
- 패턴 이름 없이 이 설계를 설명할 수 있는가?
- 요구사항이 하나 더 추가될 때, 이 패턴 덕분에 **고치지 않아도 되는 파일**은 무엇인가?
