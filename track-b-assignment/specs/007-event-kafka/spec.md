# Spec 007. 주문 이벤트 발행과 소비 (Kafka)

> 확장 spec (001~006 이후). 권장 시간 90분. 선택 근거는 ADR-0002.

## 배경 / 목적

주문이 접수·취소·체결되면 다른 시스템(알림, 정산, 이력 조회)이 이를 알아야 한다.
주문 서비스가 이들을 직접 호출하지 않도록 **도메인 이벤트를 Kafka로 발행**하고, 소비자가 이를 받아 처리한다.
메시지 시스템은 "최소 한 번(at-least-once)" 전달을 기본으로 가정한다.

## 기능 요구사항

- **FR-007-1** 주문 **접수 / 취소 / 체결** 시 이벤트를 발행한다. 이벤트 스키마(필드, 버전)는 plan에서 설계하고 계약 문서에 남긴다.
- **FR-007-2** DB 변경과 이벤트 발행은 **함께 성공하거나 함께 실패**한 것처럼 보여야 한다.
  - DB 트랜잭션이 롤백되면 이벤트는 나가지 않는다.
  - 브로커가 잠시 불가해도 주문 접수 자체는 실패하지 않고, 복구 후 이벤트가 **유실 없이** 발행된다.
- **FR-007-3** 소비자: 이벤트를 받아 **주문 이력(타임라인) 조회 모델**을 만든다. 주문별 이력을 조회하는 API를 제공한다.
- **FR-007-4** 소비자는 **멱등**하다. 같은 이벤트를 여러 번 받아도 이력은 한 번만 쌓인다.
- **FR-007-5** 같은 주문의 이벤트는 **발생 순서대로** 처리된다.
- **FR-007-6** 처리에 계속 실패하는 메시지는 정해진 횟수만큼 재시도한 뒤 **격리(DLT)** 한다. 격리된 메시지는 로그/조회로 확인할 수 있다.
- **FR-007-7** `docker compose up`에 Kafka가 포함된다. (`docker-compose.yml`의 `kafka` 서비스, 현재는 `kafka` 프로필)

## 수용 기준

- **AC-007-1** Given 주문 접수 When 트랜잭션 커밋 Then 토픽에 "주문 접수" 이벤트가 1건 발행된다.
- **AC-007-2** Given 주문 접수 중 예외로 롤백 When 처리 종료 Then 이벤트가 발행되지 않는다.
- **AC-007-3** Given 브로커 불가 When 주문 접수 Then 주문은 성공하고, 브로커 복구 후 이벤트가 발행된다.
- **AC-007-4** Given 같은 이벤트 2회 수신 When 소비 Then 주문 이력은 1건만 늘어난다.
- **AC-007-5** Given 접수 → 취소 이벤트 When 소비 Then 이력은 접수, 취소 순서로 조회된다.
- **AC-007-6** Given 처리 불가능한 메시지 When 소비 Then 재시도 후 DLT로 이동하고 다음 메시지 처리는 계속된다.
- **AC-007-7** ADR-0002에 발행 방식과 전달 보장 수준(at-least-once / exactly-once)의 선택 근거가 있다.

## 범위 밖

- 스키마 레지스트리, Avro/Protobuf (JSON으로 충분)
- 이벤트 소싱 (이벤트를 원본 데이터로 쓰는 방식)
