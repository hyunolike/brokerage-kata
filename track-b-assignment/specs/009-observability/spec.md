# Spec 009. 관측성 (선택)

> 확장 spec. 권장 시간 60분.

## 배경 / 목적

운영 중 "주문이 왜 실패했는지", "락 때문에 느려지고 있는지"를 **로그와 지표로** 답할 수 있어야 한다.

## 기능 요구사항

- **FR-009-1** 헬스 체크: 애플리케이션, DB, Redis(, Kafka) 상태를 확인할 수 있다.
- **FR-009-2** 지표: Prometheus 형식으로 수집할 수 있다. 기본 지표(HTTP, JVM, 커넥션 풀) 외에 **비즈니스 지표**를 추가한다.
  - 주문 접수 수, **거부 사유별** 주문 수 (잔고 부족, 호가 단위 위반 등)
  - 락 대기 시간 분포(003), 이벤트 발행 지연(007, 해당 시)
- **FR-009-3** 요청 추적: 모든 로그에 요청 단위 추적 ID가 찍히고, **에러 응답에도 같은 ID**가 담겨 사용자 문의를 로그로 역추적할 수 있다.
- **FR-009-4** `docker compose`로 Prometheus + Grafana를 띄워 대시보드 1개(주문 처리량, 거부율, p95 응답 시간, 락 대기 시간)를 볼 수 있다.

## 수용 기준

- **AC-009-1** 헬스 체크 응답에 DB와 Redis 상태가 포함된다.
- **AC-009-2** 잔고 부족 주문 후 지표 엔드포인트에 거부 사유별 카운터가 증가해 있다.
- **AC-009-3** 에러 응답의 추적 ID로 서버 로그에서 해당 요청의 로그를 찾을 수 있다.
- **AC-009-4** 락 대기 시간이 히스토그램(또는 타이머)으로 노출된다.

## 범위 밖

- 분산 트레이싱 백엔드(Jaeger/Tempo) 구축, 알림 규칙
