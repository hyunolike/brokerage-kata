# p1. 주문 접수 (Order Intake)

> 도메인 모델링 + 점진적 요구사항 추가 · 제한 시간 **50분** (4단계)

## 배경

증권사 주문 시스템의 가장 앞단, **주문 접수 모듈**을 만든다.
처음에는 단순한 지정가 주문만 받지만, 요구사항이 단계마다 추가된다.
단계가 올라갈수록 "이전 설계가 변경을 얼마나 쉽게 받아들이는가"가 드러난다.

## 단계 구성

| 단계 | 파일 | 권장 시간 |
|---|---|---|
| 1 | `stages/stage-1.md` | 15분 |
| 2 | `stages/stage-2.md` | 10분 |
| 3 | `stages/stage-3.md` | 15분 |
| 4 | `stages/stage-4.md` | 10분 |

> ⚠️ 현재 단계를 끝내기 전에는 다음 단계 파일과 다음 단계 테스트 파일(`Stage{N}Test.java`)을 열지 않는다.

## 평가 포인트

- **변경에 강한 설계** — 주문 유형·상태가 늘어날 때 기존 코드를 얼마나 덜 고치는가
- **상태 전이 표현** — 허용되지 않는 전이를 코드 구조로 막는가 (if 나열 vs 상태 객체/enum 메서드 등)
- **검증 위치** — 검증 로직이 어디에 있고 왜 거기에 있는가 (생성자, 값 객체, 서비스)
- **실패 표현** — 어떤 규칙을 어겼는지 호출자가 구분할 수 있는가
- 테스트 이름만 읽어도 요구사항이 보이는가

## 시작 방법

```bash
./kata start p1          # 타이머 시작 + 현재 단계 안내
```

1. **타이머 시작** — `./kata start p1`
2. **질문 목록 작성** — `NOTES.md`의 "질문 목록"에 모호한 점을 5분 안에 적는다
   (Claude에게 `/interviewer`로 면접관 역할을 시키면 답을 받을 수 있다)
3. **구현** — `Stage{N}Test.java`의 `@Disabled`를 지우고 테스트부터 채운 뒤 구현
4. **다음 단계** — `./kata next p1` (현재 단계 테스트가 모두 통과해야 넘어간다)
5. **회고** — 마지막 단계가 끝나면 `/retro p1`
